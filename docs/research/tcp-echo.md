# Research Question：两台"设备"怎么传第一字节？（Month 2 环节 1）

## Problem

Month 1 的记忆闭环全在单机内：解析 → 检索 → 排序 → 持久化。
规格书第 5 章要求两台设备同步各自的记忆库（P2P 协同），
第一步连"跨进程传一段文本"都还没做过。

最小问题：**两个进程之间怎么传数据？传之前要解决哪些概念？**

## Hypothesis

- 用 TCP 而非 UDP：记忆同步丢一条 = 丢一段认知，必须可靠、有序、面向连接
- 先打通"回显"（echo）作为最小验证：客户端 send -> 服务端 recv ->
  服务端 sendall -> 客户端收满——确认数据真的到达并原路返回
- 本环节只验证协议语义（Python），同步协议（帧格式/去重/合并）留下一环节；
  端侧 C++ 实现是规格书 L4 的后续目标

## Background

**TCP 三次握手（408 高频考点）**：
SYN -> SYN+ACK -> ACK。为什么不是两次：第二次握手后服务端已
分配连接资源，若客户端的 SYN 是过期重传的（网络延迟导致），
两次握手会让服务端建立一条客户端根本不需要的僵尸连接，浪费资源；
第三次握手让服务端确认"客户端确实想连"，过期 SYN 无法通过这一关。

**TCP 是字节流，不是报文（本环节踩到的最深坑）**：
- recv(1024) 返回的字节数 ≠ 一条消息。一次 send 的数据可能被拆成
  多次 recv；两次 send 可能合并成一次 recv（粘包）。
- 实证：客户端发 3600 字节中文，服务端按 1024 分块 recv + 分块回显，
  客户端单次 recv 只拿到第一块 1024 字节，decode 直接 UnicodeDecodeError
  （多字节字符被截断）。
- 回显场景的解法：客户端知道自己发了多少字节，循环 recv 收满。
  这是特例；通用解法是"长度前缀"帧格式（4 字节长度 + payload），
  留到同步协议环节（技术债 #19）。

**并发连接**：
单线程 accept 循环会被第一个不发送的客户端阻塞（accept 之后 read 阻塞）。
V1 用 ThreadPoolExecutor 每连接一线程；V2 换 selectors 或 C++ epoll。

**Windows 环境的连接拒绝行为**：
对"bind 但未 listen"的端口 connect，Linux 立即 RST（ConnectionRefused），
Windows 沙箱表现为超时（TimeoutError）——测试断言放宽为"快速失败且抛
OSError"，验证的核心是客户端不挂死。

## Experiment

1. `net/echo_server.py`：TCP 回显服务端
   - socket(AF_INET, SOCK_STREAM) + SO_REUSEADDR + bind + listen(5)
   - accept 循环 + ThreadPoolExecutor(8) 并发处理
   - handle_client：循环 recv -> sendall 回显；recv 返回 b'' 时判定
     对端正常关闭（四次挥手完成）
2. `net/echo_client.py`：回显客户端
   - create_connection（内部完成三次握手）
   - 循环 recv 收满 expected 字节再 decode
3. 单测 6 个：单消息往返、中文往返、6 客户端并发隔离、
   同连接多轮会话、长消息（3600 字节验证分块）、不可达端口快速失败

## Result

- `python -m pytest tests/unit -q`：**135 passed**（累计 129 + 6）
- 真实双进程验证（服务端 -m 模块方式后台启动，客户端两次连接）：
  - "你好，SynapseMatrix" -> 回显一致
  - "记忆同步需要可靠传输" -> 回显一致
- 长消息测试抓到并修复了真实的粘包/截断 bug（见 Background）

## Analysis

- 本环节明确了三条必须带进同步协议的设计约束：
  1. 消息必须有边界 -> 长度前缀帧（技术债 #19）
  2. 发送必须保证全部写完 -> send_all 封装（技术债 #20）
  3. 文本编码统一 UTF-8，任何一端编码不一致都会乱码
- 线程模型是 V1 妥协：个人端侧并发 <8 够用；多线程有 GIL 与上下文
  切换开销，C++ epoll 是规格书 L4 的终点
- 端口/地址：默认绑 127.0.0.1（隐私优先，端侧不对外暴露），
  P2P 阶段再引入加密与鉴权

## Conclusion

"两台设备传第一字节"已通：TCP 回显链路可用、可测、有真实 bug 教训。
通信底座（字节流、握手、并发模型、编码约束）已建立，
下一环节在此之上定义同步协议：帧格式 + 记忆增量同步 + 冲突处理。

## Next Question

字节能传了，怎么传"记忆"？同步协议要解决：
- 帧格式：怎么让接收方知道一条记忆在哪结束（长度前缀？）
- 增量：两台设备各有一半记忆，怎么只传差额而不是全量
- 冲突：同一记忆两边都改过，以谁为准（规格书 5.2 冲突解决策略）
